# estimetry

[English](README.md) | **Русский**

Сравнивает оценки работ с фактическими трудозатратами при разработке с AI-агентами и использует этот опыт в следующей оценке.

CLI называется `estimetry`, короткий псевдоним — `emt`.

## Установка

Нужны:
- Node.js 22.12 или новее;
- git;
- [Claude Code](https://docs.claude.com/en/docs/claude-code) — пока единственный AI-инструмент, который поддерживает estimetry.

```sh
npm install -g estimetry
emt --version
```

Ставьте глобально. Хуки, которые записывает `init`, запускают эту установку по её путям, поэтому им не мешают ни менеджер версий (asdf, nvm), выбравший для проекта другую Node.js, ни программа без `PATH` вашей оболочки.

Для обновления: `npm install -g estimetry@latest`, затем один раз `emt upgrade` (см. [После обновления estimetry](#после-обновления-estimetry)).

> estimetry в версии 0.x: команды и формат хранения ещё могут меняться между минорными версиями. Что изменилось и что сделать после обновления, написано в [CHANGELOG.md](CHANGELOG.md).

## Начало работы

1. В корне репозитория выполните `estimetry init`. Команда ставит хуки Claude Code и скиллы `/emt-…`.
2. Начните там новую сессию Claude Code и спросите, сколько займёт задача, или выполните `/emt-estimate`. Агент создаёт задачу, оценивает её по частям и сохраняет оценку, когда вы её одобрите.
3. Выполните `/emt-start` и работайте как обычно. Хуки измеряют время агентов и ваше собственное время; его показывает `emt status`.
4. Когда работа сделана, выполните `/emt-close`. Агент закрывает задачу и спрашивает, почему факт отличается от оценки.

Каждая закрытая задача делает следующую оценку обоснованнее: `emt similar` находит похожие прошлые задачи, а `emt calibrate` даёт ваш личный коэффициент, когда таких задач накопится достаточно.

## Справка

`emt --help` перечисляет все команды, включая вложенные (`task new`, `estimate save`, `parallel on`), по этапам: настройка, задачи и оценки, измерение, закрытие. У каждой — её опции, обязательные отмечены. В конце — примеры обычного порядка работы.

`emt <command> --help` или `emt help <command>` показывает одну команду целиком, например `emt help task new`.

Тот же список со всеми флагами — в [справочнике команд](#справочник-команд) в конце README.

## Настройка проекта: `estimetry init`

Выполните в корне репозитория:

```sh
estimetry init
```

В терминале команда задаёт несколько вопросов:
- какие AI-инструменты настроить (пока Claude Code);
- процесс разработки (OpenSpec или никакого);
- как делиться данными с командой;
- ставить ли git-хук.

`estimetry init --no-interactive` берёт флаги и значения по умолчанию вместо вопросов; так же ведёт себя любой запуск в CI или без терминала. Повторный запуск безопасен: он обновляет то, что ставил, и не трогает остальное.

### Что ставится

| Что | Куда | Кто получает |
|---|---|---|
| Хуки на 12 событий Claude Code, каждый запускает эту установку (`<node> <estimetry> hook claude-code <event>`, иначе `estimetry hook claude-code <event>` из `PATH`) | `.claude/settings.local.json` | вы |
| Скиллы `estimetry`, `emt-estimate`, `emt-start`, `emt-extra`, `emt-parallel`, `emt-manual`, `emt-close`, `emt-retro` (они же команды `/emt-…`) | `~/.claude/skills/` (или `$CLAUDE_CONFIG_DIR/skills/`) | вы, во всех проектах |
| Id проекта и процесс разработки | `.estimetry/config.yaml` | команда; закоммитьте его, чтобы клоны репозитория были одним проектом |

С `--shared-hooks` хуки идут в `.claude/settings.json`, а скиллы — в `.claude/skills/` проекта. В `CLAUDE.md` между `<!-- estimetry:start -->` и `<!-- estimetry:end -->` добавляется напоминание запускать `/emt-estimate`, прежде чем называть срок. Эти файлы проект коммитит, поэтому их получает вся команда.

С `--track-commits` в каталог хуков репозитория ставится хук `post-commit`. Учитываются `core.hooksPath`, ворктри и husky (`.husky/post-commit`). Существующий хук сохраняет своё содержимое: estimetry добавляет свой блок между `# >>> estimetry >>>` и `# <<< estimetry <<<`. Хук запускает estimetry в фоне, поэтому коммиты его не ждут. Коллеги без estimetry ничего не замечают. Личный хук (в `.git` или в каталоге хуков вне репозитория) запускает эту установку по её путям, как и хуки Claude Code, поэтому коммит из IDE, запущенной из Dock, тоже записывается. Хук, который проект коммитит (husky, `core.hooksPath` внутри репозитория), путей вашей машины не содержит, и ему нужен `estimetry` в `PATH`.

Данные задач никогда не попадают в репозиторий. Задачи, оценки и журнал событий лежат в `~/.local/share/estimetry/` или в `ESTIMETRY_HOME`, если он задан.

### Флаги

| Флаг | Значение |
|---|---|
| `--tools <ids>` | AI-инструменты через запятую: `claude-code` (псевдоним `claude`) |
| `--flow <id>` | `openspec` или `none`; по умолчанию определяется сам (`openspec/` в корне — значит OpenSpec) |
| `--share <mode>` | `none`, `calibration` или `cards`; пока только сохраняется |
| `--track-commits` / `--no-track-commits` | поставить или снять git-хук |
| `--shared-hooks` / `--no-shared-hooks` | поставить для всей команды или только для себя |
| `--force` | перезаписать сгенерированные скиллы, которые вы правили |
| `--no-interactive` | не задавать вопросов |
| `--json` | вывести отчёт в JSON |

Повторный запуск сохраняет то, что уже стоит: если git-хук или общая установка есть, `estimetry init` без флагов их оставляет. Чтобы снять, выполните `estimetry init --no-track-commits` или `estimetry init --no-shared-hooks`.

### Что полезно знать

- **Ваши правки сгенерированных скиллов сохраняются.** В каждом сгенерированном скилле есть `metadata.generatedBy` и хеш содержимого. Если вы его правили, init оставляет вашу версию и показывает её как `skipped`; `--force` перезаписывает. Файл с тем же именем, созданный не estimetry, не трогается никогда.
- **Изменённый хук — ваш.** estimetry узнаёт свои хуки по команде, которую записывает: пути установки с запасным `estimetry hook claude-code` или только это начало команды. Если вы её изменили, init считает хук вашим и добавляет свой рядом.
- **`settings.local.json` может не игнорироваться git.** Claude Code добавляет `**/.claude/settings.local.json` в ваши глобальные исключения git, только когда сам пишет этот файл. Если файл создал init и git его не игнорирует, init предлагает добавить ту же строку. С `--no-interactive` только предупреждает.
- **Хуки запускают ту установку, которая выполняла `init`.** `npm install -g` под той же Node.js заменяет её на месте. После установки estimetry под другую Node.js или удаления той, что выполняла `init`, выполните `emt upgrade`: до этого хуки запускают старую установку или вызывают `estimetry` из `PATH`. При запуске через `npx` или на Windows init путей не записывает, и хукам нужен `estimetry` в `PATH`. Хуки также запоминают каталог данных того `init`, если в их окружении не задан `ESTIMETRY_HOME`: `init` с временным `ESTIMETRY_HOME` направит туда и хуки проекта.

## Оценка задачи

Спросите агента, сколько займёт задача, или выполните `/emt-estimate`. Прежде чем назвать хоть одну цифру, агент:
1. согласует с вами тип задачи и технологии, которые она действительно затрагивает;
2. набрасывает части плана и запускает `emt similar` — похожие закрытые задачи с их оценками, фактом, доп. работами и уроками;
3. запускает `emt calibrate` — ваши коэффициенты и тот, который оценка может применить;
4. показывает оценку по частям и на чём она основана, а сохраняет её через `emt estimate save` только после вашего одобрения.

```sh
emt similar --type feature --stack typescript,node --hours 8
emt calibrate --type feature --stack typescript,node
emt calibrate --type feature --revise     # для переоценки задачи в работе
```

- **Похожесть** складывается из общих технологий (половина веса), типа первой оценки и, с `--hours`, размера. Для каждой задачи видно, из чего сложилась её похожесть. Без `--stack` учитывается стек проекта.
- **Коэффициент** — медиана отношения факта к оценке в первом срезе, где хватает закрытых задач: по типу, затем по технологии. Общий срез смешивает любую работу и показывается только для справки. Если задач меньше `calibration.minTasks` (по умолчанию 5), оценка — **без калибровки**, и агент об этом говорит.
- **Калиброванная оценка** умножает все три числа каждой части на коэффициент и записывает его (`calibrated: true`, `calibration.coefficient`), чтобы следующий коэффициент считался от оценки до умножения. Запас добавляется только в пессимистичные часы: доп. работы, которые вы поглотили, уже есть в коэффициенте.
- **Ничего не записывают** `emt similar` и `emt calibrate`; `calibration.json` обновляют закрытия и `emt rebuild`.
- **Сменился email.** Калибровка личная, по `author.id` в `config.yaml`. Перечислите прежние id, чтобы их карточки остались вашими:

  ```yaml
  author:
    id: new@example.com
    aliases: [old@example.com]
  ```

## Измерение задачи

Когда задача начата (`emt start`), хуки Claude Code пишут её сессии в журнал задачи. `emt status` показывает измеренный на сейчас факт: время агентов, ваше время и насколько точны цифры.

### Что учитывается

- **Время агента** — пока главный агент работает над ходом или работает сабагент, включая долгие инструменты.
- **Ваше время** — пока сессия за вами: вы смотрите результат и пишете следующий промпт. Паузы дольше порога простоя не учитываются.
- **Не учитывается** — команды, оставленные работать в фоне после того, как агент закончил ход (`run_in_background` или сабагент, ждущий свою фоновую задачу). Тогда работает машина, а не агент.

### Насколько точен факт

Некоторые промежутки решает правило, а не событие: 20 минут тишины после ответа агента могут быть и вашим разбором результата, и вашим отсутствием. `emt status` показывает диапазон, в котором лежит факт:

```
fact         29h 43m of 58h 30m (51%)
uncertainty  27h 53m – 34h 0m (21% of the fact, above the 5% target)
```

- **Нижняя граница** не считает сомнительные промежутки, которые правила засчитали: тишину от половины порога до порога, инструменты дольше двух порогов, начало хода, к которому сессия присоединилась посередине.
- **Верхняя граница** добавляет сомнительные промежутки, которые правила не засчитали: паузы до двух порогов, хвост хода или сабагента, не сообщившего о конце, долгие ожидания, закончившиеся без длительности.

Оценки и калибровка сравниваются с самим фактом; диапазон лишь говорит, насколько он может сдвинуться. Обычно большую часть диапазона дают ваши паузы после законченного хода: ничто не фиксирует, работали ли вы тогда, поэтому они остаются открытыми.

### Логи сессий, токены и стоимость

Claude Code ведёт лог каждой сессии. estimetry читает его, когда сессия заканчивается (а также на `/clear` и `/resume`) и перед закрытием задачи, и оставляет в журнале задачи только то, что нужно:
- когда начинались и заканчивались ходы агента и сабагенты: ход, конец которого хуки пропустили, заканчивается там, где его заканчивает лог, а сессия, присоединившаяся посередине, начинает ход там, где его начинает лог;
- токены по моделям с их временем и общую стоимость сессии.

Тексты лога — промпты, ответы, ввод и вывод инструментов, описания и типы сабагентов — в журнал не читаются никогда.

`emt status` и карточка показывают токены задачи и её стоимость, а также у скольких её сессий был лог. Если задаче принадлежит только часть токенов сессии (сессия началась до `emt start` или служила и другой задаче), задача получает соответствующую долю стоимости сессии: каждый вид токенов взвешивается по его цене относительно входного токена, а стоимость помечается как приблизительная.

Стоимость — это итог, который сам Claude Code записывает в лог сессии, по ценам API. На подписке это не то, что вы платите: читайте её как меру для сравнения задач между собой, а не как расходы.

Сессии, которые закончились до установки этой версии, читаются при закрытии задачи. Claude Code удаляет логи через 30 дней; для более долгих задач увеличьте `cleanupPeriodDays` в его настройках.

### Какой задаче служит сессия

- **Одна задача в работе** — сессия привязывается к ней сама.
- **Несколько задач в работе** — агент получает id сессии в её начале и спрашивает вас, какая это задача. Затем он выполняет `emt attach <task> --session <id>`. Для первой задачи сессии её работа с начала задачи тоже учитывается, как при привязке, которую сессия делает сама. Той же командой работающую сессию переключают на другую задачу; время до и после переключения уходит в нужную задачу.
- **Нет задач в работе** — время сессии хранится в журнале проекта и не идёт ни в какую задачу. Начните задачу, хотя бы `emt start --at "<когда начали>"`, и работа сессии с этого момента перейдёт в неё.

### Перезапуски и параллельные сессии

Хуки находят проект по каталогу, в котором работает Claude Code, а не по id сессии.

- **После перезапуска** (VS Code, сбой, перезагрузка) у новой сессии новый id, и она привязывается заново по правилам выше: при одной задаче в работе время продолжает идти в неё без всяких действий. При нескольких ответьте агенту, какая это задача: после привязки работа новой сессии с начала задачи тоже учитывается.
- **Ход, оборванный сбоем,** не получает конца. Его хвост закрывается по порогу простоя и показывается как неопределённость (`± …` в `emt status`). Время между сбоем и перезапуском не учитывается.
- **Две сессии на одной задаче** обе пишут в её журнал. Пересекающееся время агентов считается один раз, поэтому факт короче суммы работы двух агентов. Включите параллельный режим (`emt parallel on --agents 2`): тогда калибровка использует последовательный эквивалент — сумму работы агентов.
- **Две сессии на двух задачах** после `emt attach` служат каждая своей задаче. Коммит уходит в задачу сессии, активной последней: git-хук не знает, какая сессия его сделала. Если обе коммитят в один момент, коммит может попасть в другую задачу. Это влияет только на объём кода в карточке, не на время.

### Код в другой рабочей копии или репозитории

Агент может работать в одном репозитории, где лежат артефакты OpenSpec, а писать код в другом месте.

- **Время и прогресс плана** от этого не страдают: время идёт в задачу сессии, а план читается там, где лежат артефакты.
- **Git-ворктри** зарегистрированной рабочей копии принадлежит её проекту — с закоммиченным `.estimetry/config.yaml` или без него: задача, начатая в ворктри, — задача этого проекта, и сессия, открытая в основной рабочей копии, её видит. Отдельный клон без конфига — отдельный проект.
- **План задачи, которую ведут в ворктри,** читается в рабочей копии, где лежат её чейнджи (группы её оценки и всех переоценок), — а если в копиях они разные, то там, где их меняли последними. Так даже тогда, когда сессия работает в основной рабочей копии: процент выполнения, завершение чейнджа, отметки и объём кода при закрытии. Ворктри без своего `.estimetry/config.yaml` берёт флоу из других рабочих копий проекта.
- **Коммиты в ворктри** записываются в задачу: у ворктри общие git-хуки репозитория (при `init --track-commits`). Объём кода при закрытии меряется в рабочей копии задачи, где бы ни запускался `emt close`: коммиты, достижимые из её `HEAD`, и её незакоммиченные изменения. Незакоммиченные изменения других ворктри не видны.
- **Другой репозиторий** относится к задаче, только если вы его добавите: выполните в нём `estimetry init --track-commits` и `emt attach <task>`. Тогда его коммиты записываются, а его код меряется при закрытии.

Объём кода — только самопроверка: он никогда не меняет факт и коэффициенты.

### Отметки

Каждые 20 минут работы отметка записывает состояние плана (чекбоксы `tasks.md` OpenSpec), `HEAD` и незакоммиченные изменения — всё из рабочей копии задачи. Отметки пишут только фоновые хуки. Интервал задаётся в `~/.local/share/estimetry/config.yaml`:

```yaml
measurement:
  checkpointMinutes: 20   # от 10 до 30
```

После отметки агенту вместе с вашим следующим промптом напоминают записать работу вне плана через `/emt-extra`.

### Прогресс плана

`emt status` показывает и то, какая часть плана выполнена:

```
plan            51% done by changes (58h 30m of 58h 30m in groups)
  not started   close-retro-cards, estimate-mode
changes         4 done, last hooks-and-flows 2026-11-01 (approx.)
```

- **Части связываются через `group`.** Часть оценки, у которой `group` — имя чейнджа OpenSpec, связана с этим чейнджем в любом проекте задачи. Архивный чейндж считается выполненным на 100%, активный — по отмеченным чекбоксам, ещё не созданный — на 0%. Процент взвешивается по наиболее вероятным часам связанных частей.
- **План задачи** — её активные чейнджи плюс архивные с датой не раньше дня перед стартом задачи. Более старый архив с тем же именем относится к прежней работе.
- **Группы без чейнджа** показываются как `not started`, как `possible typo`, если есть чейндж с похожим именем, или как `archived before start`.
- **Без групп** (или без оценки) план считается по чекбоксам всех его чейнджей и помечается как не связанный с оценкой.
- **Не отслеживается**, если флоу проекта — `none` или неизвестный, у проекта нет `.estimetry/config.yaml` или его нет на этой машине. Для задачи из нескольких проектов процент считается по проектам, которые estimetry может прочитать, а остальные перечислены под `not tracked`: их группы могут выглядеть не начатыми, хотя они сделаны.
- **Несколько рабочих копий** проекта (ворктри, клоны): план читается в рабочей копии задачи — той, где лежат её чейнджи (см. [Код в другой рабочей копии или репозитории](#код-в-другой-рабочей-копии-или-репозитории)); если такой нет — в той, где вы работаете.

Чейндж завершён, когда его каталог появляется в архиве, как бы он туда ни попал: `openspec archive`, скилл, который его перенёс, или вы в терминале. Следующий вызов хука сессии, привязанной к задаче, записывает это с моментом переноса. Чейнджи, которые уже лежали в архиве, когда estimetry впервые смотрит на задачу, записываются только с датой и помечаются `(approx.)`. Чейндж, который вернули из архива, больше не считается завершённым. Процент показывается и в начале сессии (`plan 51% done`), и его записывает `emt parallel on`.

## Переоценка

Когда задача начата, её оценка — это план, с которым сравнивается факт, и `emt estimate save` не даст её изменить. Если план оказался неверным, а объём и срок остаются прежними — ошибка в проекте решения, упущение анализа, — переоцените её:

```sh
emt estimate revise plan2.yaml --reason "design was wrong" --category missed-analysis --spent exclude --lost-from "2026-11-02 10:00"
```

`emt task show <task>` показывает части действующей оценки (с `--json` — в формате файла оценки): начните новую оценку с них.

- `--spent include` — сделанная работа засчитывается в новую оценку.
- `--spent exclude` — работа с `--lost-from` (по умолчанию со старта или прошлой переоценки) до переоценки (`--at`, по умолчанию сейчас) выброшена. Она не удаляется: `emt status` показывает её отдельно как потерянную и сравнивает с новой оценкой только учтённый факт.
- `--covers <id>` — доп. работа, уже записанная за ту же потерю, чтобы потеря не посчиталась дважды. Только с `--spent exclude`, и одну доп. работу может покрыть только одна переоценка. Команда перечисляет доп. работы, записанные в окне, с их id, чтобы их можно было назвать.
- Архивные чейнджи выброшенной работы уходят из плана: они не дают ни процента, ни завершения, ни предложения закрыть. Чейндж, заархивированный позже заново, считается как обычно.

Первая оценка остаётся в журнале и в карточке: калибровка сравнивает с ней весь факт, поэтому поздняя переоценка не может сделать оценку правильной задним числом. Переоценённую оценку тоже меряют — против учтённого факта (см. [Калибровка](#калибровка)). Если заказчик согласовал больший объём или срок, используйте `emt renegotiate`.

## Закрытие задачи

Задача закрывается только с вашего согласия. Когда чейндж задачи уходит в архив, агент получает заметку с вашим следующим промптом и спрашивает, был ли он последним и закрывать ли задачу. Сам он задачу никогда не закрывает.

```sh
emt close            # показывает факт и план, затем спрашивает
emt close --yes      # без терминала (агент): только после вашего согласия
emt close --at "2026-11-02 18:00"   # работа закончилась раньше
emt close --abandoned               # задачу бросили; в калибровку она не идёт
```

Закрытие записывает объём кода и план, завершает параллельный режим и отпускает сессии задачи: сессия, закрывшая задачу, не переходит на другую задачу сама, пока не начнётся заново или пока вы не выполните `emt attach <task> --session <id>`.

Затем проведите ретро с агентом (`/emt-retro`): почему факт отличается от оценки и один урок на будущее.

```sh
emt retro --reason "manual-testing: two devices instead of one" --reason "API docs were outdated" --lesson "plan manual testing per platform"
```

Причина, которая начинается с id части оценки (`manual-testing:`), относится к этой части. Повторный `emt retro` заменяет ретро.

- **С заказчиком согласовали больше работы.** `emt renegotiate "Payments v2" --description "refunds added"` закрывает задачу как есть и создаёт новую на остаток, связанную с ней. Оцените и начните новую задачу как обычно.
- **Закрыли по ошибке.** `emt reopen T-3` снова открывает задачу; её карточка пропадает до следующего закрытия.
- **Ручное время части.** `emt manual 40m "testing on device" --part manual-testing` засчитывает время в эту часть оценки.
- **Закрытые задачи** перечисляет `emt task list --closed`; `emt task show T-3` показывает карточку.

### Карточка

Каждая закрытая задача получает карточку в `~/.local/share/estimetry/cards/<task>.yaml`, около 50 строк. В ней:
- оценка и факт, в том числе по частям оценки;
- доп. работы и параллельный режим;
- объём кода — строки рабочего кода, тестов, конфигов и документации;
- ретро.

Время делится между частями по чекбоксам, которые их чейнджи закрыли между отметками. Время, которое не может забрать ни одна часть, показывается как `unattributed`.

У переоценённой задачи сохраняются обе оценки: `estimate` и `parts` — первая оценка, `currentEstimate` и `currentParts` — действующая на момент закрытия. В карточке перечислены и все переоценки с работой, потерянной в их окне, и тем, сколько было учтено на момент каждой, а учтённый факт стоит рядом с полным. Время делится между частями текущей оценки с момента последней переоценки; то, что было учтено до неё, показывается как `before revision`. Доп. работы, названные в `--covers`, перечислены отдельно — как покрытые переоценкой.

Объём кода считает записанные коммиты задачи, ещё достижимые из `HEAD`, плюс незакоммиченное. Без записанных коммитов он считает ваши коммиты со старта задачи. Сгенерированные файлы (lock-файлы, `*.g.dart`, `dist/` и подобные) не учитываются. Строки — только самопроверка: они никогда не меняют факт и коэффициенты.

Названия, описания и ретро лежат в отдельном разделе карточки `text`, отдельно от цифр.

### Калибровка

`calibration.json` хранит ваши коэффициенты, посчитанные по вашим карточкам:
- отношение факта к оценке — общее, по типу задачи и по технологии (медиана, среднее, число задач);
- доля доп. работ по категориям и сколько объёма добавили пересогласования;
- насколько точно был спрогнозирован объём кода;
- какие виды частей выходят за оценку.

Коэффициент, основанный меньше чем на 5 задачах, показывается, но не применяется. Минимум задаётся в `config.yaml`:

```yaml
calibration:
  minTasks: 5
```

Задачи в параллельном режиме учитываются с последовательным эквивалентом. Брошенные задачи и задачи только с ручным временем не учитываются.

Переоценённые задачи дают две точности:
- главный коэффициент сравнивает весь факт с **первой** оценкой, по типу этой оценки: это то число, которое получил менеджер;
- `revised` сравнивает учтённый факт с **текущей** оценкой: насколько хороша была оценка, сделанная при переоценке, и как далеко в работе обычно случаются переоценки;
- `revisions` показывает по типу задачи, категории и `--spent`, насколько переоценки увеличивают оценку и сколько работы выбрасывают.

Части переоценённой задачи учитываются, только если до переоценки ушло не больше 5% её учтённого факта. Задачи с `--spent exclude` не участвуют в объёме кода и строках в час: откаченные строки ничего не говорят о размере задачи.

`emt rebuild` пересобирает снимки задач, карточки и `calibration.json` из журналов — например, после обновления, изменившего формулу.

### Что никогда не сохраняется

Журнал хранит, когда что-то происходило, а не что было сказано или сделано: никаких текстов промптов, ввода и вывода инструментов, команд, сообщений коммитов. Коммиты записываются как хеш, родители, `patch-id` и строки по файлам. Из логов сессий сохраняются время, число токенов по моделям и стоимость; лог, который не удалось прочитать, оставляет только код в `errors.log`.

### После обновления estimetry

Выполните один раз `emt upgrade` из любого каталога. Команда заново устанавливает estimetry во все рабочие копии всех зарегистрированных проектов на этой машине, включая ворктри. Каждая копия сохраняет свои выборы: инструменты, флоу, личную или общую установку, хук коммитов. Команда показывает, что изменится, и спрашивает подтверждение; без терминала нужен `--yes`. Копия, где estimetry не устанавливали, пропускается, как и копия, которой нет на этой машине. При общей установке план предупреждает, что меняются файлы, которые проект коммитит. Чтобы обновить только один проект, выполните `emt init` внутри него.

До этого хуки продолжают работать: обновление под той же Node.js заменяет установку, которую они запускают. Старым остаётся только то, что записал `init`: настройки хуков в проектах, скиллы и, при общей установке, напоминание в `CLAUDE.md`. В начале сессии в проекте, установленном старой версией, агент получает подсказку предложить `emt upgrade`; сам он её не запускает.

Обновляйте все установленные копии estimetry сразу. Карточки, записанные старой версией, пересобираются из журналов при следующем закрытии, `emt task show` или `emt rebuild`. Карточка новее версии не даёт старой estimetry перезаписать `calibration.json` и показывается вместо этого; версии до этой проверки пропускают такие карточки молча, поэтому не закрывайте ими задачи.

### Настройка

- **`emt init`** — настроить estimetry в этом проекте: хуки, скиллы и команды AI-инструмента, конфиг проекта
  - `--tools <ids>` — AI-инструменты через запятую (claude-code)
  - `--flow <id>` — процесс разработки: openspec или none (по умолчанию определяется сам)
  - `--share <mode>` — чем делиться с командой: none, calibration, cards
  - `--track-commits` — установить git-хук post-commit
  - `--no-track-commits` — удалить git-хук post-commit
  - `--shared-hooks` — установить для всей команды, в файлы, которые проект коммитит
  - `--no-shared-hooks` — установить только для себя (по умолчанию)
  - `--force` — перезаписать сгенерированные скиллы, которые вы правили
  - `--no-interactive` — не спрашивать; брать флаги и значения по умолчанию
- **`emt upgrade`** — после обновления estimetry: заново установить его во все проекты на этой машине, каждый со своими выборами
  - `--yes` — пользователь уже согласился (нужно без терминала)
- **`emt rebuild [task]`** — пересобрать снимки задач, карточки и calibration.json из журналов

- **`emt task new <title>`** — создать задачу в текущем проекте
  - `--type <type>` — тип задачи: feature, integration, bugfix, refactor, infra, migration, research
  - `--ticket <key>` — ключ тикета во внешнем трекере
- **`emt task list`** — список задач текущего проекта
  - `--all` — задачи всех проектов
  - `--closed` — вместе с закрытыми
- **`emt task show <task>`** — показать задачу
- **`emt similar`** — найти закрытые задачи, похожие на новую: их оценки, факт, доп. работы и уроки
  - `--type <type>` — тип новой задачи
  - `--stack <labels>` — технологии, которые задача затрагивает, через запятую; по умолчанию стек проекта
  - `--hours <hours>` — предварительные наиболее вероятные часы новой задачи, до калибровки
  - `--limit <n>` — сколько задач показать (по умолчанию: "5")
- **`emt calibrate`** — показать ваши коэффициенты для типа и стека и тот, который можно применить к оценке
  - `--type <type>` — тип оцениваемой задачи
  - `--stack <labels>` — технологии, которые задача затрагивает, через запятую; по умолчанию стек проекта
  - `--revise` — для переоценки задачи в работе: коэффициент оценок, сделанных во время работы
- **`emt estimate save <file>`** — сделать файл оценки планом задачи (можно, пока работа не началась)
  - `--task <id>` — id задачи; по умолчанию единственная новая или оценённая задача проекта
- **`emt estimate revise [file]`** — переоценить план задачи в работе: старая оценка остаётся, новая сравнивается с учтённым фактом
  - `--reason <text>` — почему изменился план: короткая формулировка, согласованная с пользователем
  - `--category <category>` — new-requirement, missed-analysis, rework или environment
  - `--spent <policy>` — include: сделанная работа учитывается; exclude: работа в окне потерь выброшена

  - `--at <time>` — с какого момента действует новая оценка; по умолчанию сейчас
  - `--task <id>` — id задачи; по умолчанию единственная задача в работе в этом проекте

### Измерение

- **`emt start [task]`** — начать работу над задачей; с этого момента её трудозатраты записываются
  - `--at <time>` — задним числом (ISO 8601 или "YYYY-MM-DD HH:MM"), для работы, начатой раньше
- **`emt attach <task>`** — подключить задачу к текущему проекту (для задач в нескольких репозиториях)
  - `--session <id>` — ещё и привязать эту сессию AI-инструмента к задаче (когда в работе несколько задач)
- **`emt manual <duration> <description>`** — записать время, которого хуки не видели: вашу работу вне сессий агента или работу агента с --agent
  - `--at <time>` — когда работа закончилась (ISO 8601 или "YYYY-MM-DD HH:MM"); сливается с измеренным временем
  - `--agent` — время агента, например работа до установки estimetry
  - `--task <id>` — id задачи; по умолчанию единственная задача в работе в этом проекте
  - `--part <id>` — id части оценки, к которой относится время, например manual-testing
- **`emt extra <description>`** — записать работу вне оценённого плана
  - `--category <category>` — одна из: new-requirement, missed-analysis, rework, environment (обязательно)
  - `--time <duration>` — ваша прикидка, сколько это стоило; факт не меняет
  - `--lines <n>` — сколько строк кода это заняло
  - `--change <name>` — чейндж, к которому это относится
  - `--task <id>` — id задачи; по умолчанию единственная задача в работе в этом проекте
- **`emt parallel on`** — включить параллельный режим; записывает, сколько бюджета потрачено
  - `--reason <text>` — почему работа идёт параллельно
  - `--agents <n>` — число агентов
  - `--parts <ids>` — id частей оценки, которые делаются параллельно, через запятую
  - `--task <id>` — id задачи; по умолчанию единственная задача в работе в этом проекте
- **`emt parallel off`** — выключить параллельный режим
  - `--task <id>` — id задачи; по умолчанию единственная задача в работе в этом проекте
- **`emt status [task]`** — показать факт задачи на сейчас: агенты, вы, неопределённость и оценка
  - `--json` — вывести JSON (длительности в минутах)

### Закрытие

- **`emt close [task]`** — закрыть задачу после согласия пользователя; затем выполнить `emt retro`
  - `--at <time>` — когда работа закончилась (ISO 8601 или "YYYY-MM-DD HH:MM"); по умолчанию сейчас
  - `--abandoned` — задачу бросили: в калибровке она не используется
  - `--yes` — пользователь уже согласился её закрыть (нужно без терминала)
- **`emt reopen <task>`** — открыть задачу, закрытую по ошибке
- **`emt retro [task]`** — записать, почему факт отличается от оценки, и один урок
  - `--reason <text>` — причина, можно в виде "<part id>: <text>"; повторяется для нескольких (обязательно)
  - `--lesson <text>` — один урок для следующей оценки (обязательно)
- **`emt renegotiate <title>`** — заказчик согласился на дополнительную работу: закрыть задачу как есть и начать новую на остаток
  - `--task <id>` — задача, по которой договорились заново; по умолчанию единственная задача в работе в этом проекте
  - `--description <text>` — что изменилось; по умолчанию название
  - `--category <category>` — категория доп. работы, по умолчанию new-requirement
  - `--type <type>` — тип новой задачи; по умолчанию тип исходной
  - `--at <time>` — когда закончилась исходная работа; по умолчанию сейчас
  - `--yes` — пользователь уже согласился (нужно без терминала)
